# Общий реестр: GitHub Pages + Supabase

GitHub хранит и публикует интерфейс. Supabase хранит общий реестр и проверяет вход. Данные клиентов не включены в публикуемые файлы сайта. Максим и Шамиль работают с одной базой; открытая вкладка проверяет изменения раз в 15 секунд, если в ней не редактируется форма. До создания проекта Supabase и настройки подключения общий сайт не готов к работе.

## 1. Создайте проект Supabase

Откройте https://supabase.com/dashboard и создайте аккаунт, организацию и проект. Выберите подходящий регион и тариф в интерфейсе сервиса. Пароль базы храните у себя: в сайт, GitHub и чат он не нужен.

Дождитесь готовности проекта. В SQL Editor выполните **полное содержимое `schema.sql` из этой папки**. Оно создаёт таблицы, ограничения и правила доступа RLS. Схема не содержит данных клиентов и может быть выполнена повторно. Не отключайте RLS: публичный ключ сам по себе не является защитой базы.

## 2. Создайте две учётные записи

В Authentication отключите самостоятельную регистрацию новых пользователей. В разделе Users создайте две учётные записи с почтами Максима и Шамиля. Задайте пароли в защищённом интерфейсе Supabase; не отправляйте их в чат. Если требуется подтверждение почты, завершите его или используйте подтверждённое создание пользователя администратором.

Вернитесь в SQL Editor и выполните запрос ниже, **заменив только две почты** реальными адресами:

```sql
INSERT INTO public.dela_members(user_id, display_name)
SELECT id, 'Максим' FROM auth.users WHERE lower(email) = lower('maxim@example.com')
ON CONFLICT (user_id) DO UPDATE SET display_name = EXCLUDED.display_name;

INSERT INTO public.dela_members(user_id, display_name)
SELECT id, 'Шамиль' FROM auth.users WHERE lower(email) = lower('shamil@example.com')
ON CONFLICT (user_id) DO UPDATE SET display_name = EXCLUDED.display_name;

SELECT display_name FROM public.dela_members ORDER BY display_name;
```

Результат должен содержать ровно две нужные записи. Если их нет, проверьте почты и наличие пользователей. Создание пользователя в Auth **без** включения в `dela_members` не даёт доступа к делам. Оба участника имеют одинаковые права; индивидуальных ролей и журнала изменений пока нет.

## 3. Укажите публичное подключение

В настройках проекта найдите **Project URL** и **Publishable key** (или legacy **anon public** key).

Откройте файл `cloud-config.js` в ветке `gh-pages` репозитория `artgrotesk/dela` и заполните:

```js
window.DELA_CLOUD_CONFIG = Object.freeze({
  url: 'https://PROJECT_ID.supabase.co',
  key: 'sb_publishable_ВАШ_ПУБЛИЧНЫЙ_КЛЮЧ'
});
```

Project URL и publishable/anon key предназначены для открытого клиентского приложения. **Не используйте** `service_role`, `sb_secret_…`, пароль базы или пароли пользователей. Служебные ключи обходят RLS и не должны попадать в GitHub или браузер. Приложение отказывается работать со служебным ключом.

Для последующих сборок скопируйте те же **публичные** параметры в `pages/cloud-config.js` исходного проекта, чтобы следующая публикация не затёрла подключение. Не публикуйте каталог исходного проекта целиком: `seed.json` содержит исходные клиентские заметки. Публичная ветка должна содержать только результат сборки `dist/`.

## 4. Включите GitHub Pages

В репозитории `artgrotesk/dela` откройте **Settings → Pages**. Выберите **Deploy from a branch**, ветку **gh-pages**, папку **/ (root)** и сохраните. Дождитесь успешной публикации. Если интерфейс GitHub показывает ограничение доступности Pages, потребуется решить его в настройках аккаунта/тарифа; размещение автоматически не включалось через API.

Используйте фактический адрес, который покажет GitHub после публикации. В Supabase Authentication → URL Configuration задайте этот адрес как Site URL. Откройте сайт: после настройки подключения появится форма входа.

При будущих обновлениях используйте `python scripts/build_pages.py`: он собирает только интерфейс в `dist/`, без записей клиентов. Не публикуйте файлы `.data/`, `.env`, SQLite, резервные копии или JSON-экспорт.

## 5. Перенесите семь дел

Скачайте подготовленный файл `dela-private-import.json` из чата на свой компьютер. Он не включён в ветку сайта. После входа одного из двух участников нажмите **Импортировать** и выберите этот файл.

Импорт выполняется один раз в пустую общую базу, атомарно. Он перенесёт семь дел, семь задач и статусы 28 документов. Подтверждённых оплат и расходов в исходном реестре нет. Повторный импорт не может заменить уже заполненную базу. Статусы документов сохраняются, их идентификаторы при переносе могут измениться.

Второй пользователь входит со своей почтой и видит тот же реестр. Не нужно импортировать файл отдельно для каждого участника.

## 6. Проверьте работу на реальном адресе

- Без входа дела не видны.
- Максим и Шамиль входят каждый со своей почтой и видят один набор дел.
- Задача, созданная одним участником, появляется у второго после обновления страницы или очередной проверки изменений.
- Изменения сохраняются после закрытия браузера и повторного входа.
- Посторонняя учётная запись не получает доступ.
- JSON-экспорт работает. Храните резервные копии отдельно и не добавляйте их в GitHub.

Это обязательная проверка после создания настоящего проекта. Локальные проверки схемы и браузера не подтверждают готовность ещё не созданного проекта Supabase.

## Проверки разработчика

```sh
python tests/cloud_browser.py
python tests/shared_database.py
```

Первая проверка использует имитацию Supabase HTTP API: вход, отдельные браузеры, общие задачи, импорт и выход. Вторая поднимает временный PostgreSQL 17 через Docker и проверяет реальные ограничения и RLS (с тестовой реализацией `auth.uid()`): доступ двух участников, запрет посторонним, атомарный импорт и запрет оплат услуг прошлых лет. Внешний Supabase не используется и не считается проверенным.

Учётная сессия хранится в sessionStorage вкладки; после её закрытия может потребоваться повторный вход. Сброс пароля и управление участниками в первой версии выполняются администратором через Supabase. Вложений, ЭДО и автоматического мониторинга судебных дел пока нет.
